# Mathematical constant generation

The range constants in `stdlib/std/math.dodo` and `stdlib/std/math/trig.dodo`
are generated by [`scripts/generate_math_constants.py`](../../../scripts/generate_math_constants.py).
The generator uses Python's standard library, integer arithmetic, and exact
rational-to-binary64 conversion. It contains no precomputed mathematical digits,
copied tables, or calls to a host math library, and needs no network access.

From the repository root:

```sh
python3 scripts/generate_math_constants.py          # print without reading source blocks
python3 scripts/generate_math_constants.py --check  # verify without writing
python3 scripts/generate_math_constants.py --write  # regenerate source blocks
```

The script also works from other directories. CI runs `--check`; normal builds
and math runtime tests use the checked-in values and do not need Python.

## Derivation

For an integer `q >= 2`, evaluate the elementary series

```text
atan(1/q)  = sum(k >= 0, (-1)^k / ((2*k + 1) * q^(2*k + 1)))
atanh(1/q) = sum(k >= 0,        1 / ((2*k + 1) * q^(2*k + 1)))
pi        = 16*atan(1/5) - 4*atan(1/239)     (Machin's identity)
ln(2)     = 2*atanh(1/3)
```

Each term is enclosed between consecutive integers after scaling by `2^p`.
Summation stops when the first omitted term is below one scaled unit. The
alternating remainder is bounded by that term and has its sign. The positive
remainder is below two scaled units, since successive terms have ratio less
than `1/q^2 <= 1/4`. Adding these errors gives integer lower and upper bounds
for each series, and hence for `pi` and `ln(2)`.

The reduction table represents `floor((2/pi) * 2^1584)` as 66 base-`2^24`
digits, most significant first. Integer division at both bounds of `pi` must
give the same 1,584-bit integer before its digits are emitted.

The logarithm split is defined by

```text
LN_2_HIGH = floor(ln(2) * 2^32) / 2^32
LN_2_LOW  = RN(ln(2) - LN_2_HIGH)
```

Here `RN` means binary64 rounding to nearest, ties to even. The high part has
32 significant bits and 21 trailing zero significand bits, allowing exact
products with the small integer exponents used by `log` and `exp`. The low
part is rounded from the high-precision residual, not from binary64 `LN_2`.

The same calculation supplies `INV_LN_2 = RN(1/ln(2))` and the exponential
cutoffs. For the overflow cutoff, use `RN(ln(MAX_FINITE))`, where

```text
MAX_FINITE     = 2^1024 * (1 - 2^-53)
ln(MAX_FINITE) = 1024*ln(2) - 2*atanh(1/(2^54 - 1))
```

The underflow cutoff is `ln(2^-1075) = -1075*ln(2)`, rounded toward positive
infinity. Half the smallest subnormal is `2^-1075`; the existing strict `<`
test therefore needs the first binary64 input above this boundary. Rounding
it to nearest instead would change the cutoff by one ulp.

Every floor or binary64 conversion must agree at both interval endpoints.
The entire computation runs at both `p = 2048` and `p = 4096`, and both runs
must agree. The intervals certify the emitted digits and rounding decisions;
agreement between two precisions is an additional check. This certifies the
constants, not the accuracy of the runtime math functions.

## Replacement and provenance review

The math modules were introduced in commit
`6a6a6fd00b252bf216d6e71cb45dd78ea984b6e7`. Their original notice identified
the split `ln(2)` constants and the `2/pi` digits as borrowed from fdlibm,
and described the algorithms as independent implementations. The independent
generator replaces those inputs. All 66 digits and both split constants
match the preceding source exactly. The reciprocal and exponential cutoffs
were included in generation as well; their binary64 values also match:

| Constant | Binary64 bits |
| --- | --- |
| `LN_2_HIGH` | `0x3fe62e42fee00000` |
| `LN_2_LOW` | `0x3dea39ef35793c76` |
| `INV_LN_2` | `0x3ff71547652b82fe` |
| `EXP_OVERFLOW_LIMIT` | `0x40862e42fefa39ef` |
| `EXP_UNDERFLOW_LIMIT` | `0xc0874910d52d3051` |

Review of both complete math modules, their introduction, related tests and
documentation, and repository searches for fdlibm attribution found no
additional retained fdlibm implementation or approximation tables:

- `log`, `exp`, `log1p`, and `expm1` use direct series and composition, with
  none of the fitted polynomial coefficients or evaluation schemes in
  fdlibm's [`e_log.c`](https://www.netlib.org/fdlibm/e_log.c),
  [`e_exp.c`](https://www.netlib.org/fdlibm/e_exp.c),
  [`s_log1p.c`](https://www.netlib.org/fdlibm/s_log1p.c), or
  [`s_expm1.c`](https://www.netlib.org/fdlibm/s_expm1.c).
- The trigonometric reducer multiplies all 66 limbs using integer arithmetic
  and extracts a quadrant and 128 fractional bits. It has none of the staged
  split-`pi/2` subtraction, floating-point partial convolution, adaptive
  recomputation, or output compression in
  [`e_rem_pio2.c`](https://www.netlib.org/fdlibm/e_rem_pio2.c) and
  [`k_rem_pio2.c`](https://www.netlib.org/fdlibm/k_rem_pio2.c).
- Sine and cosine use Taylor recurrences; tangent divides those results.
  Arctangent uses an alternating series, and inverse sine/cosine compose
  `sqrt` and `atan2`. The corresponding fdlibm fitted kernel coefficients,
  arctangent split tables, and inverse-trigonometric rational approximations
  are absent.
- Roots use fixed Newton iterations, `hypot` uses a normalized ratio, and
  powers use repeated squaring or compose `log` and `exp`. Rounding uses
  `trunc` and comparisons; classification and scaling use binary64 fields.
  These differ from the corresponding fdlibm implementations. Integer
  helpers use checked arithmetic, Euclid's algorithm, and restoring square
  root.
- Remaining literals express public mathematical constants, binary64 layout
  and powers of two, series iteration counts, or elementary reduction
  boundaries (`sqrt(2)` and `sqrt(2)-1`). There are no other coefficient or
  argument-reduction tables in the math modules. Reference test vectors are
  produced by the separately documented MPFR generator.

This review and the independent generation are the basis for removing the
math-specific fdlibm notice and attribution. Historical revisions containing
the borrowed material keep their notice in Git history. The separate
`stdlib/std/LICENSE.musl` belongs to the decimal-formatting implementation and
is retained in full, including its discussion of upstream math code.
